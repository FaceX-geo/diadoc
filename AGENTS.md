# Локальный архив Диадока

## Обновление данных

- Если пользователь прямо попросил первоначальную сборку архива, выполнить её и продолжать после остановки без повторного согласования. Эта инструкция сама по себе не разрешает новую загрузку: учитывать запрос текущего пользователя.
- В последующих задачах перед обращением к Диадоку спросить: «Подтянуть новые данные из Диадока или работать с текущим локальным архивом?»
- Если пользователь уже явно попросил обновить/синхронизировать/догрузить документы, это ответ «подтянуть»; повторно не спрашивать.
- Без ответа работать с локальным архивом. Не запускать сетевую синхронизацию по умолчанию или по расписанию.
- Читать Диадок только через обычный авторизованный интерфейс браузера и DOM. Не использовать интеграционный API, скрытые HTTP-эндпоинты, копирование cookies или токенов.
- Соблюдать доступ текущего пользователя и выбранной организации. Обрабатывать входящие, исходящие и внутренние. Не подписывать, не согласовывать, не отправлять, не аннулировать и не удалять документы.

## Надёжность архива

- Источник локального состояния — SQLite и манифесты в `archive/`. Метаданные без проверенных файлов не считать полным архивом.
- Не скачивать повторно уже проверенные неизменившиеся документы. Дедупликация по boxId + letterId + documentId; файлы по SHA-256.
- Изменившиеся статусы записывать в историю. Новую версию комплекта хранить отдельно от предыдущей. Содержимое оригиналов и подписей не менять.
- Периодически сверять весь список метаданных после разрешения пользователя: у старого документа тоже могут измениться подписи/статус. Не останавливаться на первом знакомом документе.
- Проверять все три раздела, пагинацию, незавершённые загрузки, архивы/файлы и свободное место. При остатке менее 3 GiB приостановить загрузки и сообщить пользователю.
- На сбое сохранять контрольную точку; повторять только недостающие/непроверенные комплекты. Не объявлять завершение до проверки покрытия и всех файлов.
- Архив, персональные данные, журналы выгрузки и базу не коммитить. Все коммиты только от macniel1520; без прямого указания новую ветку не создавать, работать в main. GitHub Actions здесь не нужны; если появятся, все jobs — только подходящие подтверждённые FaceX self-hosted runners, по умолчанию `[self-hosted, production-2u]`.

- Контейнеры с явной платформой `linux/arm64` запускать только на подтверждённом FaceX self-hosted macOS ARM64 runner, который online и доступен репозиторию. Если такого runner нет — сообщить о блокере; не подменять платформу AMD64, Rosetta или QEMU.
- Остальные Linux-контейнеры собирать и запускать нативно на FaceX Linux self-hosted runner, по умолчанию `[self-hosted, production-2u]`. Сохранять явную целевую платформу в Dockerfile/Compose/Buildx. Проверять каждый job во всех `.github/workflows/`; после изменения workflow подтверждать фактический запуск на self-hosted runner.
