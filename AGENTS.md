# Локальный архив Диадока

## Обновление данных

- Если пользователь прямо попросил первоначальную сборку архива, выполнить её и продолжать после остановки без повторного согласования. Эта инструкция сама по себе не разрешает новую загрузку: учитывать запрос текущего пользователя.
- В последующих задачах перед обращением к Диадоку спросить: «Подтянуть новые данные из Диадока или работать с текущим локальным архивом?»
- Если пользователь уже явно попросил обновить/синхронизировать/догрузить документы, это ответ «подтянуть»; повторно не спрашивать.
- Без ответа работать с локальным архивом. Не запускать сетевую синхронизацию по умолчанию или по расписанию.
- Читать Диадок только через обычный авторизованный интерфейс браузера и DOM. Не использовать интеграционный API, скрытые HTTP-эндпоинты, копирование cookies или токенов.
- Соблюдать доступ текущего пользователя и выбранной организации. Обрабатывать входящие, исходящие и внутренние. Не подписывать, не согласовывать, не отправлять, не аннулировать и не удалять документы.

## Надёжность архива

- Источник локального состояния — SQLite и манифесты в `archive/`. Метаданные без проверенных файлов не считать полным архивом.
- Не скачивать повторно уже проверенные неизменившиеся документы. Дедупликация по boxId + letterId + documentId; файлы по SHA-256.
- Изменившиеся статусы записывать в историю. Новую версию комплекта хранить отдельно от предыдущей. Содержимое оригиналов и подписей не менять.
- Периодически сверять весь список метаданных после разрешения пользователя: у старого документа тоже могут измениться подписи/статус. Не останавливаться на первом знакомом документе.
- Проверять все три раздела, пагинацию, незавершённые загрузки, архивы/файлы и свободное место. При остатке менее 3 GiB приостановить загрузки и сообщить пользователю.
- На сбое сохранять контрольную точку; повторять только недостающие/непроверенные комплекты. Не объявлять завершение до проверки покрытия и всех файлов.
- Архив, персональные данные, журналы выгрузки и базу не коммитить. Все коммиты только от macniel1520; без прямого указания новую ветку не создавать, работать в main. GitHub Actions здесь не нужны; если появятся, все jobs — только подходящие подтверждённые FaceX self-hosted runners, по умолчанию `[self-hosted, production-2u]`.

- Контейнеры с явной платформой `linux/arm64` запускать только на подтверждённом FaceX self-hosted macOS ARM64 runner, который online и доступен репозиторию. Если такого runner нет — сообщить о блокере; не подменять платформу AMD64, Rosetta или QEMU.
- Остальные Linux-контейнеры собирать и запускать нативно на FaceX Linux self-hosted runner, по умолчанию `[self-hosted, production-2u]`. Сохранять явную целевую платформу в Dockerfile/Compose/Buildx. Проверять каждый job во всех `.github/workflows/`; после изменения workflow подтверждать фактический запуск на self-hosted runner.

## OpenAI: обязательный прокси и запрет прямого обхода

Постоянное поручение Александра Корнилова от 17.11.2026. Применяется во всех
репозиториях FaceX к новым и изменяемым интеграциям OpenAI, серверным заданиям,
скриптам и диагностике. Канон: `FaceX-geo/infra-as-code`,
`.agents/policies/openai-proxy.md`. Вложенные инструкции не ослабляют правило.

- Все прикладные обращения к OpenAI выполняются только через утверждённый
  SOCKS5-прокси: основной маршрут FI, дополнительный DE. Нужны удалённое DNS
  через SOCKS (`socks5h` либо эквивалент SDK) и проверка TLS имени/сертификата.
  Прямой сетевой запрос к OpenAI запрещён, включая диагностику и retry.
- Нет конфигурации, неверный URL/протокол, отсутствует SOCKS-поддержка,
  недоступен прокси или отказала авторизация — OpenAI-функция блокируется с
  безопасной ошибкой. Никогда не создавать запасной клиент без прокси, не
  повторять напрямую и не отключать TLS-проверку. Остальные функции приложения
  могут продолжать работу, если их независимость подтверждена.
- Использовать единый явно настроенный транспорт для каждого используемого
  SDK/HTTP/WebSocket клиента, включая async, streaming, загрузку файлов и
  фоновые worker. `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` сами по себе не доказывают
  защиту: исключить обход через `NO_PROXY`, окружение, другой клиент, redirect
  или пользовательский `base_url`. Разрешать только проверенные OpenAI origins;
  не пересылать Authorization произвольному redirect/CDN. Подписанные внешние
  загрузки имеют отдельный проверенный allowlist и не получают API-ключ.
- Ключи OpenAI и доступы прокси доступны только backend. Браузер/мобильный клиент
  обращается к своему backend; секреты не попадают в bundle, Git, отчёты,
  исключения, argv, логи, трассировки или пользовательские ответы. Маскировать
  полный credential-bearing URL. Не печатать окружение клиента.
- Организационные GitHub Secrets: `OPENAI_PROXY_URL_FI` и
  `OPENAI_PROXY_URL_DE` — полные URL с реквизитами. Это доступы прокси,
  не OpenAI API-ключи. Существующие API-ключи не заменять и не централизовать
  автоматически. Нечувствительные Variables: `OPENAI_PROXY_REQUIRED=true`,
  `OPENAI_PROXY_PRIMARY=FI`, `OPENAI_PROXY_SECONDARY=DE`,
  `OPENAI_PROXY_DIRECT_FALLBACK=false`. Они описывают политику, а не выключатель:
  значение false/отсутствие переменной не разрешает прямой трафик.
- GitHub Free не предоставляет организационные Secrets/Variables закрытым
  репозиториям Actions. Runtime получает реквизиты через утверждённый серверный
  secret service либо защищённый файл своего окружения. Не покупать тариф,
  не раскрывать репозиторий и не копировать production-секреты в repository-wide
  secrets. Наличие организационного секрета не означает runtime-доставку.
- Переключение FI → DE допускается только через второй явно настроенный прокси
  с ограниченным числом попыток и общим deadline. Не повторять автоматически
  запрос после возможного принятия сервером или начала stream без доказанной
  безопасной семантики повтора. Ошибки API 401/403/429 не лечить сменой страны,
  обходом ограничений или бесконечным retry. При отказе авторизации прокси
  остановить этот маршрут, не перебирать пароли.
- Приёмка на разрешённом FaceX executor: положительный HTTPS-запрос; отсутствие
  конфигурации; невалидный URL; выключенный прокси; неправильная авторизация
  в изолированном mock; `NO_PROXY=*`; redirects; каждый sync/async/stream/worker
  путь. Отрицательные проверки должны доказать НОЛЬ прямых соединений к OpenAI,
  отсутствие утечки ключа и корректный отказ, а не только ожидаемый exception.
- Для строгой гарантии на уровне системы нужен отдельный проверенный egress
  policy: процесс OpenAI может выходить только к допущенным прокси, включая
  IPv4/IPv6; остальные зависимости перечислены явно. Не считать AGENTS,
  переменные или тесты SDK сетевым firewall. Изменять сеть/production только
  по отдельному адресному допуску, сохраняя работоспособность других служб.
- Перед изменением существующей интеграции проверить её реальный транспорт и
  способ доставки секретов. Отдельно сообщать: инструкция установлена,
  секрет сохранён, код проверен, runtime переключён, прямой egress запрещён.
  Не заявлять последние три результата без проверки. Уже работающие агенты
  должны перечитать правило; запись файла не обновляет их контекст автоматически.
